# План диагностики снижения подписок после обновления `ticker_source/base_pools.json`

## Контекст
- После выравнивания поля `dex` в `ticker_source/base_pools.json` наблюдается почти двукратное падение количества подписок на CEX и существенное снижение по DEX (остались только V2 на Ethereum).
- Архитектура: скринер строит подписки на основе списка тикеров и пулов, загруженных из файлов конфигурации (`ticker_source`, `configs`, `internal/util/symbol_loader.go`, `internal/launcher`).

## Цели
1. Выявить точку, где теряются подписки (парсинг конфигураций, нормализация данных, построение подписок в лаунчере/коннекторах).
2. Определить, связано ли падение с новым форматом поля `dex` или с сопутствующими некорректными данными.
3. Подготовить гипотезу для фикса.

## План действий
1. **Сравнение конфигураций**
   - Сравнить текущий `ticker_source/base_pools.json` с предыдущей версией (git diff, бэкапы) и проверить, что для каждого пула сохранены сети, пары и идентификаторы.
   - Проверить соответствие полей `dex` ожиданиям кода (`internal/util/symbol_loader.go`, `internal/dex/.../pool_source_helpers.go`).
2. **Проверка загрузки данных**
   - Пройти по коду загрузки базовых пулов (`internal/util/symbol_loader.go`, `internal/config/...`) и убедиться, что новый формат `dex` корректно маппится на внутренние структуры.
   - Добавить временные логи или использовать существующие, чтобы увидеть количество загруженных пулов по каждой бирже.
3. **Анализ нормализации и подготовки данных**
   - Изучить `internal/redisclient/normalize.go` и смежные места, где могут фильтроваться или отбрасываться записи после изменения поля `dex`.
   - Проверить, не ломается ли маппинг на канонические имена DEX/CEX в `internal/assets/provider.go` и связанных справочниках (`configs/assets/tokens.yaml`).
4. **Трассировка построения подписок**
   - Проследить путь от загруженных пулов к созданию подписок в `internal/launcher` (например, `register_dex.go`, `context.go`), `internal/dex/pricing`, и далее к коннекторам (`internal/dex/Etherium/Uniswap/*`, `internal/exchange/*`).
   - Использовать логи (`screner.log`, `run_core.log`) для определения, на каком этапе отбрасываются DEX-подписки.
5. **Валидация через тесты/скрипты**
   - Запустить релевантные тест-скрипты (`test_scripts/uniswap/...`, `test_scripts/redis/*`) или интеграционные тесты, чтобы воспроизвести численность подписок на локальной среде.
   - При необходимости подготовить временный скрипт для подсчёта подписок после загрузки базовых пулов.
6. **Формирование гипотез и фикса**
   - На основе найденной точки отказа сформулировать гипотезы (например, ожидание разных значений `dex`, регистр, пробелы, отсутствующие маппинги).
   - Подготовить план исправления и оценить влияние на связанные компоненты (коннекторы, нормализация, алертинг).

## Ожидаемые артефакты
- Итоговый отчёт о точке сбоя и предлагаемом решении.
- Обновлённые тесты/скрипты проверки при необходимости.
