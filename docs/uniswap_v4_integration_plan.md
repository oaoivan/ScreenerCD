### Итог по шагу 2.1.1

- Для Uniswap V4 вводим независимую структуру `V4Config`, чтобы не перегружать `Config` (V2) и `V3Config`, а также явно описать Pool Manager.
- Поля `V4Config` (Go-тип справа):
	- `Exchange string` — алиас биржи (используется в логах, Redis, нормализации).
	- `WSURL string` — обязательный WebSocket endpoint (Alchemy/интеграция провайдера, подстановка `${ALCHEMY_API_KEY}` поддерживается напрямую).
	- `HTTPURL string` — обязательный HTTP endpoint для `eth_call` (fallback аналог V3, также поддерживает `${ALCHEMY_API_KEY}`).
	- `PoolManager common.Address` — адрес контракта PoolManager (парсится из YAML как строка, допускается `${POOLMANAGER_V4}` — `LoadConfig` расширяет переменные окружения).
	- `PoolsPath string` — путь к JSON со списком пулов (GeckoTerminal или кастомный файл).
	- `Pools []V4PoolConfig` — опциональный inline-набор пулов из конфигурации.
	- `SubscribeBatchSize int` — размер батча при подписке (по умолчанию 150, как у V2/V3).
	- `PingInterval time.Duration` — интервал keep-alive ping (дефолт 25s).
	- `MaxMetaWorkers int` — ограничение параллельных запросов метаданных (`eth_call`).
	- `SwapOnly bool` — фильтрация по событиям Swap (аналог `DecodeSwapOnly` в V3).
	- `LogAllEvents bool` — расширенный лог фреймов (для отладки).
	- `StopOnAckError bool` — принудительное завершение при ошибке `eth_subscribe` ack.
	- `Once bool` — опциональный режим «первая котировка и стоп» (оставляем только в дебаг-билде).
	- `Registry *TokenRegistry` — ссылка на реестр активов (подставляется лаунчером, как в V2/V3).

- Структура пула `V4PoolConfig`:

	```go
			PoolID       common.Hash
			PairName     string

			BaseIsToken0 bool
			CanonicalPair string
	}
	```
	- `TokenMeta` переиспользует реализацию из V2 (адрес, символ, decimals, флаги стейбл/WETH).

### Итог по шагу 2.1.2

1. **Подготовка соединения**
	- Коннектор поднимает WS к `V4Config.WSURL`, подписывается на `eth_subscribe` c фильтром по `PoolManager`.
	- Параллельно стартует goroutine keep-alive (ping) и reader, пишущий raw frames в буферизированный канал.

2. **Обработка логов**
	- Reader передаёт сообщения в обработчик `handleRaw`, который различает ack/notification.
	- `processSwap` декодирует событие `Swap`: получает `poolId`, `amount0/amount1`, `sqrtPriceX96`, `liquidity`, `tick`, `fee`.

	- Используем `GraphPricer` (регистрация токенов заранее) и вызываем `UpdatePair(token0, token1, price, weight, now)`.

4. **Публикация котировок**
	- Публикуем `MarketData` с символами `TOKEN0TOKEN1` и `TOKEN1TOKEN0`, фильтруя <1 bp шум.

### Итог по шагу 2.1.3

- **Handshake**: используем `websocket.Dialer` с `HandshakeTimeout=15s`, сжатие включено; сразу после коннекта отправляем `eth_subscribe` на `logs` с фильтром `address = PoolManager`. Для трассировки логируем маскированный URL и JSON подписки (аналог V3).
- **Keep-alive**: отдельная goroutine каждые `V4Config.PingInterval` (дефолт 25s) шлёт `PingMessage`; reader пропускает `PongMessage`, фиксирует последний `ping/pong` таймстемп для диагностики.
- **Reader**: одна goroutine читает фреймы, складывает в канал `msgs`. При ошибке закрывает канал и прокидывает ошибку в управляющий цикл.
- **Reconnect loop**: внешний цикл с экспоненциальным backoff (старт 2s, максимум 30s), как в V3. При каждом разрыве закрываем текущее соединение, ждём `backoff` и удваиваем интервал (ограничено 30s). Счётчик реконнектов выводим в лог.
- **Ack handling**: после подписки ждём ack; если `StopOnAckError=true`, то при ошибке завершаем цикл и возвращаем ошибку, чтобы supervisor перезапустил коннектор. Без флага — пишем ошибку и продолжаем (для толерантности).
- **Rate limits Alchemy**: соблюдаем лимит в ~30 подписок/мин, поэтому подписываемся батчами `SubscribeBatchSize` (<=150) и не создаём новые соединения чаще, чем backoff позволяет. Добавляем jitter при необходимости (будет расширяемым).
- **Shutdown**: при закрытии `ctx` закрываем соединение, дожидаемся завершения reader/ping горутин и выбрасываемся из цикла без повторного коннекта.

### Итог по шагу 2.1.4

- **Кэш пула**: `PoolMeta` хранит флаги `Loaded`, `Loading`, `HasJSONMeta`, `LoadErr`. При первом событии пула проверяем `Loaded`; если нет — инициируем lazy fetch.
- **Очередь задач**: обработчик swap кладёт poolID в `metaQueue` (буфер 32). Отдельный воркер читает очередь и запускает `ensurePoolMeta(poolID)` в goroutine, соблюдая семафор `MaxMetaWorkers`.
- **ensurePoolMeta**: выполняет `eth_call` к PoolManager (`token0()`, `token1()`), затем к токенам (`decimals()`, `symbol()`), переиспользуя кеш `TokenMeta` (общий map `<address> -> meta`). Результаты обновляют `PoolMeta` под `RWMutex`.
- **Регистрация в прайсере**: после успешной загрузки вызываем `RegisterToken`/`RegisterStable` для обоих токенов, обновляем поле `Loaded` и сбрасываем `LoadErr`.
- **Timeouts/Retry**: каждый `eth_call` выполняем с `context.WithTimeout(4s)`. При ошибке записываем `LoadErr`, откладываем повтор на 15s (репаблиш в очередь), чтобы не DDoS-ить RPC.
- **Concurrency safety**: `Loading` защищён mutex-ом; повторные события пула не дублируют запрос, пока `Loading=true`. После завершения флаг сбрасывается.
- **Fallback**: если JSON уже содержит decimals/symbol, `HasJSONMeta=true` и lazy fetch пропускается, пока не понадобится верификация (флаг `VerifyPoolOrder` можно добавлять позже).
- **Metrics**: логируем успешные/ошибочные загрузки и время отклика RPC для мониторинга.

### Итог по шагу 2.1.5

- **Семафор**: используем `make(chan struct{}, V4Config.MaxMetaWorkers)` (дефолт 8). Каждая задача метаданных вызывает `acquireSem()` перед RPC и `releaseSem()` после.
- **Воркеры**: по умолчанию единый воркер читает `metaQueue` и запускает `processPool(poolID)` в отдельной goroutine. Ограничение семафором удерживает общее число параллельных `eth_call`.
- **Backpressure**: если `metaQueue` заполнен, новые события пула просто не добавляют задачу (ждём следующего свопа); таким образом не заполняем память.
- **Jitter**: между повторными попытками добавляем `time.Sleep(200-500ms)` для распределения нагрузки.
- **Metrics**: считаем gauge активных семафорных слотов и latency каждого `ensurePoolMeta`; логи `[META] acquire/release` помогают мониторить блокировку.
- **Config**: `MaxMetaWorkers` в YAML ограничивает параллелизм; при `<=0` используем дефолт 4, чтобы не перегружать RPC.

### Итог по шагу 2.1.6

- **Базовый режим**: используем статический список пулов из конфигурации (файл/inline). Это гарантирует, что каждая подписка проходит верификацию, позволяет заранее вычислить канонические пары и избегает лишних RPC.
- **Обновление списка**: при добавлении пула обновляем общий источник (`shared_pools` или отдельный `uniswap_v4` JSON) и перезапускаем коннектор. Для снижения даунтайма планируем hot-reload (см. будущий backlog), но MVP — ручной рестарт.
- **Детектор новых пулов**: опционально запускаем фонового воркера, который раз в N минут читает GeckoTerminal/API, сравнивает с текущим набором и пишет дифф в лог. Автоподписки нет, чтобы избежать подписки на неизвестные токены без валидации.
- **Fast track**: допускаем короткий список `WantedPairs` (как в тестовом скрипте) для smoke-тестов; он может заменять общий список через флаг `use_wanted_pairs_only` (будет добавлен в конфиг при необходимости).
- **Документация**: в `docs/project_documentation.md` описываем процедуру добавления пула: обновить JSON → прогнать валидатор → перезапустить сервис. Логи `[POOL] added` помогут убедиться, что новый пул поднялся.

- **7.1.2.** Использовать `util.NormalizeSpotSymbol` для тикеров перед публикацией, чтобы не нарушать ключи `price_canon:*`.
- **7.1.3.** Проверить, что worker-пулы Redis (`cmd/screener-core/main.go`) не требуют доработок, и документировать ожидаемый throughput V4.
- **7.1.4.** При необходимости добавить отдельный канал метрик по количеству сообщений V4 (по аналогии с `perExchange`).

### Итог по шагу 7.1.3

- Воркеры Redis уже нормализуют тикеры через `util.NormalizeSpotSymbol` при построении ключей `price_canon:*`, поэтому после правок в коннекторе (`emitSpot`/`emitUSD`) дополнительных изменений не требуется.
- Один swap
event V4 выдаёт до четырёх `MarketData` (две спот-направления + до двух USD), поэтому для стартового набора из 10 пулов при пиковых 2 swap/с на пул ожидается не более 80 сообщений/с.
- Текущее значение `redis_workers` (>=8) и пайплайн на 300 команд обеспечивают запас >5x: даже при 100 msg/с формируется лишь ~200 HSET/с, что укладывается в окно flush 100 мс.
- Метрика `perExchange` уже включает `uniswap_v4`, что позволяет контролировать фактическую нагрузку без дополнительных счётчиков.
