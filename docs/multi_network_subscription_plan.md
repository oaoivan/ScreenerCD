# План расширения подписок на несколько сетей и DEX

## 1. Текущее состояние
- Конфиг `dex_configs` фиксирует отдельные коннекторы `uniswap_v2`, `uniswap_v3`, `uniswap_v4`, и для каждого жёстко задана сеть `ethereum` и адреса пулов. 【F:configs/screener-core.yaml†L28-L84】
- Валидация конфига пока не учитывает многосетевой режим: `DexConfig` хранит поле `Network`, но оно используется только при загрузке реестра и фильтрации пулов. 【F:internal/config/config.go†L52-L125】
- Лаунчер регистрирует только Uniswap-коннекторы и создаёт `TokenRegistry` для одной сети, исходя из `dexCfg.Network`. 【F:internal/launcher/register_dex.go†L1-L165】
- Поток данных формирует ключи Redis в формате `price:<exchange>:<symbol>` без учёта сети; канонический ключ также не содержит сети. 【F:cmd/screener-core/main.go†L296-L323】
- Структура `MarketData` не несёт информации о сети/цепи, только `exchange`, `symbol`, `price`, `timestamp`. 【F:pkg/protobuf/arbitrage.proto†L6-L12】
- Коннекторы Uniswap формируют `MarketData.Exchange` из имени DEX и не учитывают сеть при публикации. 【F:internal/dex/Etherium/Uniswap/v4_connector.go†L315-L343】

## 2. Цели расширения
1. Позволить конфигурации включать несколько сетей и DEX для подписки, используя единую базу пулов `ticker_source/base_pools.json` как источник.
2. Обеспечить маршрутизацию данных так, чтобы в Redis и в приложении можно было различать биржу и сеть.
3. Сохранить совместимость для текущей конфигурации Uniswap на Ethereum и обеспечить плавное добавление новых коннекторов.

## 3. План внедрения

### 3.1. Анализ и подготовка источников пулов
- Расширить `ticker_source/base_pools.json`, добавив явные поля `dex` и `network` для каждого пула (совместимо с текущей структурой Gecko JSON). Убедиться, что будущие коннекторы могут фильтровать по обоим полям. (Исходный файл уже содержит `dex` и `network` — требуется задокументировать и стандартизировать.)
- Написать вспомогательную утилиту/валидатор (по аналогии с `test_scripts/assets/validate_tokens.go`) для проверки новых пулов на корректность адресов и допустимых сетей перед добавлением в общий JSON.

### 3.2. Конфигурация
- Подзадачи:
  1. Проектирование новых полей `ChainID`/`NetworkID`/`DexAlias` в `config.DexConfig`, подготовка схемы и обратной совместимости.
  2. Расширение YAML-конфига и `configs/screener-core.yaml` примеров под множественные записи с одинаковым `name`.
  3. Рефакторинг загрузчика (`LoadConfig`) и валидации для проверки уникальности `name+network`, обязательности источников пулов.
  4. Расширение `internal/assets`/`TokenRegistry` для быстрого выбора токенов конкретной сети при старте коннектора.
  5. Доработка фильтрации источников пулов (`PoolsSource`) по `dex` + `network` + `wanted_pairs` и синхронизация с `ticker_source/base_pools.json`.
  6. Обновление документации (`docs/project_documentation.md`) по добавлению сети/DEX, включая порядок обновления пулов и конфигурации.
- Пересмотреть структуру `config.DexConfig`:
  - Подзадачи:
    7. Добавить явные поля `DexAlias`, `NetworkID`, `ChainID` и методы получения нормализованных значений.
    8. Обновить `configs/screener-core.yaml` и примеры, продемонстрировав несколько `dex_configs` с одним `name` на разных сетях.
    9. Расширить `PoolsSource` фильтрами `dexes`, `networks`, `wanted_pairs_by_network`, добавить вспомогательные методы.
    10. Рефакторить `LoadConfig`/`Validate`, чтобы проверять уникальность `name+network`, наличие источника пулов и корректность новых полей.
    11. Поддержать многосетевой `TokenRegistry`: обновить `internal/assets` и связанные структуры для выбора токенов по сети/alias/chain_id.
    12. Обновить документацию (`docs/project_documentation.md`), описав процедуру добавления новой сети/DEX и работу с общим пулом.

### 3.3. Структуры данных и протокол
- Подзадачи:
  1. Обновить `pkg/protobuf/arbitrage.proto`, добавить `network`, `chain_id`, пересобрать Go-код (`generate_proto.sh`). 【F:pkg/protobuf/arbitrage.proto†L6-L12】【F:scripts/generate_proto.sh†L1-L50】
  2. Протянуть новые поля в `pkg/common/models.go`/`internal/processor` и другие потребители структур `MarketData`, синхронизировать константы и типы. 【F:pkg/common/models.go†L1-L120】【F:internal/processor/processor.go†L1-L120】
  3. Обновить коннекторы Uniswap V2/V3/V4, чтобы формировать `MarketData.Exchange` и `MarketData.Network` на основе `DexConfig` и логировать сетевые идентификаторы. 【F:internal/dex/Etherium/Uniswap/v2_connector.go†L1-L340】【F:internal/dex/Etherium/Uniswap/v4_connector.go†L315-L343】
  4. Доработать прайсер (`internal/dex/pricing`), чтобы ключи графа строились по `dex_alias`+`network`, учесть мультичейн бридж-токены. 【F:internal/dex/pricing/graph_pricer.go†L1-L220】
  5. Пройтись по лаунчеру/маршрутизации (`internal/launcher`), убедиться, что `TokenRegistry` и фабрики коннекторов передают новую сетевую метаинформацию в `MarketData`. 【F:internal/launcher/register_dex.go†L1-L165】
  6. Обновить документацию по протоколу данных (`docs/project_documentation.md`), описать новые поля и совместимость старых клиентов.

### 3.4. Поток данных и Redis
- В `cmd/screener-core` пересмотреть генерацию ключей: перейти на формат `price:<network>:<exchange>:<symbol>` и `price_canon:<network>:<canonical_symbol>:<exchange>`.
- Проверить совместимость скриптов/дашбордов, которые читают текущие ключи. Для плавной миграции можно поддерживать дублирующую запись в старый ключ в течение переходного периода.
- Обновить `redisclient` и тестовые скрипты, чтобы они понимали новый формат ключей.

### 3.5. Лаунчер и маршрутизация коннекторов
- В `internal/launcher/register_dex.go` обеспечить передачу информации о сети в коннектор (возможная реорганизация `NewTokenRegistry` с учётом нескольких сетей). 【F:internal/launcher/register_dex.go†L19-L118】
- Добавить возможность запускать разные инстансы одного коннектора (например, Uniswap V3 для Ethereum и для Base) в отдельных supervisor-процессах, используя уникальные имена (например, `uniswap_v3:ethereum`).
- Обновить логирование и метрики, чтобы идентификаторы включали сеть.

### 3.6. Тестирование и отладка
- Модифицировать интеграционные тесты/скрипты (`tests/integration`, `test_scripts/uniswap`) под новый формат конфига и данных.
- Добавить юнит-тесты на сериализацию `MarketData` и генерацию новых ключей Redis, чтобы ловить регрессии до интеграционного уровня.
- Добавить smoke-тесты для коннектора в новой сети с использованием mock WS/HTTP, проверяя, что Redis ключи формируются корректно и что `MarketData.Network` сохраняется.
- Протестировать миграцию на staging: запустить сервис с двумя сетями и убедиться, что графовый прайсер корректно обновляет цены, а Redis содержит раздельные ключи.

### 3.7. Ввод в эксплуатацию
- Подготовить процедуру миграции Redis (очистка/перенос ключей, временная синхронная запись в новый и старый формат).
- Обновить документацию по деплою и `.vscode/tasks.json`/CI сценарии, чтобы они загружали переменные окружения для разных сетей (RPC URLs, Pool Manager и т.д.).
- Настроить мониторинг по сети: дашборды должны агрегировать метрики по `network` и `dex`.
- Настроить алерты по доступности RPC-эндпоинтов и задержкам подписок, чтобы быстро ловить деградации при росте числа сетей.

## 4. Риски и контрольные точки
- **Совместимость:** необходимо обеспечить обратную совместимость или контролируемый даунтайм при переходе на новые ключи Redis.
- **Производительность:** добавление новых сетей увеличивает нагрузку на Redis и прайсинг; потребуется пересчитать `data_channel_buffer`, `redis_workers` и другие параметры. 【F:configs/screener-core.yaml†L87-L110】
- **Качество данных:** требуется строгая валидация пулов и токенов, чтобы не смешивать активы разных сетей в прайсере.
- **Безопасность:** дополнительные RPC эндпоинты для новых сетей должны быть защищены и иметь лимиты, аналогичные текущим провайдерам.

## 5. Следующие шаги
1. Согласовать формат расширенного `MarketData` и ключей Redis со смежными командами (UI, аналитика).
2. Подготовить proof-of-concept для одной новой сети (например, Base для Uniswap V3) и протестировать полный цикл.
3. После подтверждения — внедрить поддержку дополнительных DEX (PancakeSwap, Sushi, и т.д.), используя единый конфиг-подход.
