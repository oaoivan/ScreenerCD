# Uniswap v4 → Redis Data Path Analysis

## 0. Итог и фикс
- На шаге подписки WS использовался адрес PoolManager из `.env` (`POOLMANAGER_V4=0x868031d4cba8b7a8e7a3e97b4dab7fa5120e061a`), для которого `eth_getCode` возвращает `0x`, то есть контракт отсутствует. Подтверждение — запрос к Alchemy (`eth_getCode`) в `curl` показал пустой байткод.
- Реальный PoolManager для сетки Ethereum, фигурирующий в `ticker_source/base_pools.json`, — `0x000000000004444c5dc75cb358380d2e3de08a90`. Именно этот адрес выдаёт полноценный байткод (`eth_getCode` → длинный hex).
- Из-за подписки на «пустой» адрес коннектор не получал ни одного события `Swap`, поэтому пайплайн дальше (store→pricing→Redis) оставался пустым.
- Обновил `.env` (`POOLMANAGER_V4`) на корректный адрес. После перезапуска сервиса ожидаем появление строк `uniswap_v4: swap…`/`pricing update…` и рост `perExchange["uniswap_v4"]` в `metrics`, что подтвердит попадание данных в Redis.

## 1. Поток данных внутри коннектора
- `V4Connector.Run` поднимает websocket, ждёт ack и каждую входящую ноту прокидывает в `handleFrame`, который распознаёт `eth_subscription` и передаёт лог в `handleLog`.【F:internal/dex/Etherium/Uniswap/v4_connector.go†L888-L1093】
- `handleLog` отфильтровывает только события `Swap` и вызывает `handleSwapEvent` для дальнейшего разбора.【F:internal/dex/Etherium/Uniswap/v4_connector.go†L1148-L1188】
- `handleSwapEvent` декодирует payload, считает цены, вес и затем вызывает `storeSwapMetrics`. Если пул неизвестен (`c.pools` не содержит `poolID`), функция возвращает `false` и обработка завершается **до** публикации котировки.【F:internal/dex/Etherium/Uniswap/v4_connector.go†L1095-L1146】【F:internal/dex/Etherium/Uniswap/v4_connector.go†L1238-L1243】
- Лишь при успешном сохранении метрик и валидных float-ценах (`price1Valid/price0Valid`) вызывается `updatePricing`, которая публикует spot/USDT котировки через `emitSpot/emitUSD` в общий канал `out` (это `dataChannel`).【F:internal/dex/Etherium/Uniswap/v4_connector.go†L1201-L1329】【F:internal/dex/Etherium/Uniswap/v4_connector.go†L317-L343】

## 2. Попадание в общий канал
- Коннектор запускается из `buildUniswapV4`, где в `ctx.Supervisor` ему передаётся `ctx.DataChannel`; именно в этот канал коннектор кладёт `*pb.MarketData` после `emitSpot/emitUSD`.【F:internal/launcher/register_dex.go†L167-L195】
- Общий канал создаётся в `cmd/screener-core/main.go` и кладётся в `LaunchContext`, чтобы все биржевые/DEX коннекторы пользовались одной очередью сообщений.【F:cmd/screener-core/main.go†L178-L233】

## 3. Запись в Redis
- Worker pool читает из `dataChannel`, формирует батч `HSET` и пишет в Redis через `redisClient.HSetBatch`. Одновременно счётчики `totalProcessed` и `perExchange[md.Exchange]` увеличиваются для каждой полученной записи, так что любое сообщение, дошедшее до этой точки, попадёт как в метрики, так и в Redis-пайплайн.【F:cmd/screener-core/main.go†L263-L327】

## 4. Где теряются данные
- В текущем запуске потеря происходила **до** входа в коннектор: провайдер не отдавал ни одного лога, потому что подписка шла на некорректный PoolManager (`0x8680…`, код=0x). Поскольку `log_all_events=true`, в `screner.log` отсутствуют строки `uniswap_v4: swap…`/`unknown pool…`, что подтверждает отсутствие входящих событий.【screner.log】
- При корректном адресе возможные точки отбрасывания остаются прежними: не распознанный `pool_id` (см. `storeSwapMetrics` → `return false`) или невалидные цены (NaN/Inf) в `updatePricing`. Эти ветки остаются релевантны для мониторинга после фикса.【internal/dex/Etherium/Uniswap/v4_connector.go†L1095-L1146】【internal/dex/Etherium/Uniswap/v4_connector.go†L1205-L1322】

## 5. Рекомендации по диагностике
1. После перезапуска проверить, что `metrics` логирует ненулевой `perExchange.uniswap_v4` и что в Redis появляются ключи из V4 (можно через `redis-cli keys uniswap_v4:*`).
2. Сохранить привычку валидировать `POOLMANAGER_V4` запросом `eth_getCode` при обновлении окружения — это мгновенно подтверждает корректность адреса.
3. Для дальнейшего контроля оставить `log_all_events` включённым на ближайшие сессии; при стабилизации можно отключить и добавить счётчики `conversionErrors`/`unknownPool` в метрики для раннего детекта аномалий внутри коннектора.

## 6. Постобработка Redis (исправление)
- В пайплайне `HSetBatch` значения попадали в hash через промежуточную `map[string]interface{}`. Redis не гарантирует порядок полей при `HGETALL`, из-за чего при переборе “первым” значением часто оказывался `timestamp` (например, `BIOUSD=1760018762089`), хотя реальная цена лежала в поле `price`.
- Теперь пайплайн отправляет набор полей через `HSET` с сохранением исходного порядка (`price`, затем `timestamp`, …). `HGETALL` по-прежнему не детерминирован на 100%, но в Valkey/Redis 6+ возвращает поля в порядке записи — скрипты, которые читают “первый элемент = цена”, больше не спотыкаются.【internal/redisclient/client.go:64】
