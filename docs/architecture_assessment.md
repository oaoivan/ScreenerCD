# Оценка архитектуры ScreenerCD

## Текущий поток данных и обязанности
- **Прием данных (Ingestion)** – Все коннекторы CEX и DEX скомпилированы в бинарный файл `screener-core` и запускаются через общий реестр `launcher`. Каждый сборщик работает в отдельной управляющей горутине, пересылает фреймы WebSocket в общий буферизованный канал и использует логику пакетирования для соблюдения ограничений скорости, установленных площадками.【F:internal/launcher/register_cex.go†L22-L199】【F:cmd/screener-core/main.go†L223-L259】
- **Нормализация и ценообразование (Normalization & Pricing)** – `cmd/screener-core` создает единый общий канал `chan *pb.MarketData` с настраиваемой емкостью и инициализирует графовый механизм ценообразования в USD, когда включены коннекторы Uniswap, для нормализации событий пула.【F:cmd/screener-core/main.go†L178-L221】
- **Сохранение (Persistence)** – Пул горутин обрабатывает данные из общего канала, записывает необработанные (raw) и канонические хеши в Redis с использованием конвейерной обработки (pipelining) и периодически сообщает метрики пропускной способности и состояния, в то время как побочная горутина выполняет проверки работоспособности Redis.【F:cmd/screener-core/main.go†L263-L384】
- **Статические входные данные (Static Inputs)** – Базовые пулы и списки символов загружаются из общего JSON-файла, определенного в конфигурации, с каскадным использованием `shared_pools`, устаревшего файла по умолчанию или встроенных конфигураций DEX. Метаданные активов загружаются из YAML для заполнения графового механизма ценообразования.【F:cmd/screener-core/main.go†L94-L177】【F:internal/config/config.go†L203-L333】

## Оценка по ключевым критериям
### Скорость / Пропускная способность
- 👍 Прием данных через WebSocket работает конкурентно для каждой площадки с легковесными супервизорами и пакетированием, что позволяет удерживать всплески подписок в рамках лимитов бирж и поддерживать высокую скорость обработки сообщений в одном процессе.【F:internal/launcher/register_cex.go†L22-L199】
- 👍 Записи в Redis пакетируются (конвейеры `HSET` до ~300 операций) и дублируются в raw/канонические ключи, минимизируя время кругового пути (RTT) и обеспечивая O(10⁵) обновлений в минуту на стандартном оборудовании.【F:cmd/screener-core/main.go†L263-L329】
- ⚠️ Все площадки мультиплексируются в один канал Go и один пул воркеров. При пиковой нагрузке (несколько блокчейнов + тысячи пар) канал может стать узким местом, создавая обратное давление на все коннекторы равномерно, даже если всплеск происходит только на одной площадке.
- ⚠️ Обновления графа ценообразования происходят синхронно внутри горутин коннекторов; механизм ценообразования потокобезопасен, но ограничен одним процессом. Интенсивное разрешение маршрутов или поиск с большей максимальной длиной пути будут конкурировать за ресурсы CPU с потоками сетевого ввода-вывода.【F:internal/dex/pricing/graph_pricer.go†L45-L200】

### Масштабируемость / Отказоустойчивость
- 👍 Супервизоры автоматически перезапускают отказавшие коннекторы с экспоненциальной задержкой, повышая отказоустойчивость без ручного вмешательства.【F:cmd/screener-core/main.go†L24-L61】
- ⚠️ Источники конфигурации (`shared_pools`, реестр активов) считываются один раз при запуске; обновления `ticker_source/base_pools.json` или метаданных токенов требуют перезапуска бинарного файла, что усложняет динамическое масштабирование и автоматическое обновление пулов.【F:cmd/screener-core/main.go†L94-L177】【F:internal/config/config.go†L203-L333】
- ⚠️ Архитектура масштабируется вертикально: один процесс обрабатывает прием данных, ценообразование, сохранение и проверки состояния. Горизонтальное масштабирование требует дублирования всего бинарного файла и ручного разделения символов, что увеличивает операционную сложность.
- ⚠️ Redis является единой точкой отказа и единственным интерфейсом между сервисами. Буферизация за пределами Redis отсутствует, поэтому сбои блокируют весь путь приема данных, несмотря на наличие супервизоров.

### Модульность / Ориентация на микросервисы
- 👍 Лаунчеры регистрируют коннекторы декларативно, поэтому добавление новой площадки включает реализацию сборщика и маппинга protobuf без изменения `main.go`.
- ⚠️ Коннекторы, механизм ценообразования и сохранение тесно связаны через каналы в памяти. Отсутствует контракт сообщений, кроме структур protobuf, что затрудняет разделение компонентов на независимые сервисы или отдельное масштабирование коннекторов.
- ⚠️ Интерфейс Wails, арбитражные калькуляторы и последующие потребители данных неявно используют общие ключи Redis. Отсутствие явного API или шины событий мешает созданию подключаемых модулей и аудиту изменений схемы.

## Рекомендуемые улучшения
1.  **Внедрить шину событий и разделить сервисы времени выполнения** – Отправлять нормализованные котировки в надежную очередь (например, NATS, Kafka или Redis Streams) и вынести модуль записи в Redis, а также арбитражную аналитику в выделенные микросервисы. Это позволит независимо автомасштабировать "горячие" площадки, изолировать обратное давление и сделать прием данных stateless.
2.  **Реализовать динамическое управление символами и пулами** – Добавить сервис-наблюдатель, который опрашивает внешний генератор `base_pools` или получает push-обновления, публикует изменения для коннекторов и ротирует подписки без перезапусков. Горячая перезагрузка наборов символов для каждой биржи позволит избежать простоев и улучшить реакцию на добавление новых рынков.
3.  **Выделить граф ценообразования в отдельный компонент** – Предоставить сервис gRPC или IPC, который поддерживает граф маршрутизации в USD, питаемый событиями обмена DEX. Таким образом, слой приема данных будет только передавать события, а нагрузки по ценообразованию можно будет масштабировать с выделенными бюджетами CPU/памяти.
4.  **Усилить слой Redis** – Добавить настраиваемую буферизацию с упреждающей записью (например, локальная очередь с выгрузкой на диск) и многоузловой Redis (кластер или реплика с Sentinel), чтобы избежать единых точек отказа. Включить автоматические выключатели (circuit breakers), чтобы коннекторы могли корректно деградировать при недоступности Redis.
5.  **Определить четкие контракты данных** – Версионировать схемы protobuf и документировать канонические форматы ключей Redis в `docs/`, чтобы последующие модули (UI, аналитика) полагались на явные контракты. Внедрить тесты валидации схемы для защиты от случайных ломающих изменений.

## Следующие шаги
- Приоритезировать разделение с помощью шины событий, чтобы разблокировать горизонтальное масштабирование и декомпозицию на микросервисы.
- Создать прототип управления подписками с горячей перезагрузкой, используя существующие загрузчики конфигурации в качестве основы.
- Спланировать развертывание выделенных сервисов ценообразования и аналитики после того, как прием данных станет stateless.
